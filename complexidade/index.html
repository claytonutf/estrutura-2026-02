Análise de Algoritmos

Dois algoritmos podem resolver o mesmo problema — e ainda assim ter custos muito diferentes.

Para decidir qual é realmente melhor, a ciência da computação usa uma régua chamada complexidade computacional: uma forma de medir o custo de um algoritmo — em tempo e em memória — conforme o tamanho da entrada cresce.

custo = memória + tempo

01 Fundamentos

O que a análise de algoritmos tenta responder

A pergunta central é simples de enunciar e difícil de responder de forma definitiva: dá para fazer este algoritmo de um jeito mais eficiente? Como o mesmo problema costuma admitir várias soluções, é preciso uma forma justa de comparar essas soluções entre si.

Quando a diferença importa

Duas soluções para o mesmo problema raramente são igualmente eficientes. Essa diferença de custo pode se comportar de dois jeitos bem distintos:

  • Ser irrelevante quando poucos elementos são processados;
  • Crescer proporcionalmente ao número de elementos — e se tornar decisiva conforme a entrada aumenta.

custo Memória + tempo

A complexidade computacional resume o custo de aplicar um algoritmo em dois componentes: quanto espaço ele consome e quanto tempo sua execução leva. Para decidir qual algoritmo é mais eficiente, existem duas abordagens complementares — a empírica e a matemática — exploradas a seguir.

02 Métodos de comparação

Duas formas de saber qual algoritmo é melhor

A análise empírica mede o algoritmo em execução; a análise matemática estuda sua ideia, independentemente de hardware ou linguagem. Cada uma tem seu papel.

Empírica Medir a execução real

Avalia o custo a partir da execução do programa já implementado.

Vantagens
  • Mede o desempenho real numa configuração específica de máquina/linguagem;
  • Revela custos não aparentes, como a alocação de memória;
  • Permite comparar computadores diferentes;
  • Permite comparar linguagens diferentes.
Dificuldades
  • Exige implementar o algoritmo — depende da habilidade de quem programa;
  • O resultado pode ser mascarado pelo hardware ou por eventos do software;
  • É preciso escolher a natureza dos dados: reais, aleatórios ou perversos.

Matemática Estudar a ideia do algoritmo

Quando o ideal é medir o algoritmo de forma independente de hardware e linguagem, usa-se um computador idealizado que considera apenas os custos dominantes.

  • Ignora detalhes de baixo nível: linguagem, hardware, conjunto de instruções da CPU;
  • Revela como o algoritmo se comporta quando a entrada cresce;
  • Expressa a relação entre o tamanho da entrada e o tempo necessário para processá-la;
  • É o caminho usado no restante deste material.
Dados aleatórios revelam o desempenho médio; dados perversos revelam o pior caso.
03 Exemplo guiado

Contando instruções: encontrando o maior valor de um array

Para calcular o custo de um algoritmo matematicamente, contamos quantas instruções simples — atribuições, acessos, comparações, incrementos, operações aritméticas — ele executa. Comandos de seleção como o if têm custo zero: não contam como instrução.

A cada iteração — 2 instruções (i++ e a comparação seguinte), repetidas n vezes → 2n

O corpo do laço muda tudo: o pior caso

04 Simplificando a função de custo

Comportamento assintótico: descartando o que não importa

A função f(n) = 4n + 3 descreve o custo exato — mas nem todo termo é necessário para entender o que acontece quando n cresce muito. Se um algoritmo é mais rápido para entradas grandes, ele tende a continuar mais rápido também para entradas pequenas.

Duas regras de descarte

1 · Descartar constantes isoladas

O termo +3 não é afetado pelo valor de n — é apenas uma constante de inicialização. Pode ser removido sem alterar o comportamento de crescimento da função.

2 · Descartar constantes multiplicativas

O 4 que multiplica n também é descartado: ele varia conforme a linguagem e o compilador (em Pascal, por exemplo, o acesso a um array inclui uma verificação de limites que não existe em C), e não representa a ideia do algoritmo.

4n

n

O que sobra é o comportamento assintótico: como f(n) se comporta quando n tende ao infinito. O termo de maior grau sempre domina — mesmo que outros termos tenham constantes maiores. Por isso, g(n) = 1000n + 500 acaba perdendo para h(n) = n² + n + 1 a partir de um certo n, apesar da constante 1000.

Regra prática: um programa sem laços custa f(n) = 1; um laço de 1 a n custa f(n) = n; dois laços aninhados custam f(n) = n²; e assim por diante.

05 A notação mais usada

Notação Grande-O: o limite superior do pior caso

Entre as formas de análise assintótica, a notação Grande-O (O) é a mais conhecida. Ela descreve o custo do algoritmo no pior caso possível, estabelecendo um teto que o algoritmo nunca ultrapassa.

Definição formal

Uma função de custo f(n) é O(g(n)) se existem constantes positivas c e m tais que, para todo n ≥ m:

f(n) ≤ c · g(n)

Exemplo: selection sort

O selection sort percorre um array de tamanho n em busca do menor valor e o move para a posição correta, repetindo o processo para cada posição seguinte. O laço interno executa n−1, depois n−2, ... até 1 vez — uma soma que resulta em S(n) = n(n−1)/2.

Uma forma mais simples de obter um limite superior é imaginar uma versão pior do algoritmo — com o laço interno sempre executando n vezes, mesmo que isso desperdice iterações. Com dois laços aninhados de n execuções, a função de custo passa a ser f(n) = n².

Conclusão: o selection sort é O(n²) — nunca pior do que n², assintoticamente.
06 A família completa

Além do Grande-O: limites inferior, superior e o caso exato

O Grande-O não é a única notação assintótica. Cada uma responde a uma pergunta diferente sobre o comportamento de f(n).

Ω
Ômega — melhor caso

Descreve o limite assintótico inferior: f(n) é no mínimo tão custosa quanto g(n).

f(n) é Ω(g(n)) se existem c, m > 0 tais que f(n) ≥ c·g(n) para todo n ≥ m.
O
Grande-O — pior caso

Descreve o limite assintótico superior: f(n) nunca é pior do que g(n).

f(n) é O(g(n)) se existem c, m > 0 tais que f(n) ≤ c·g(n) para todo n ≥ m.
θ
Theta — limite exato

Descreve o limite firme: f(n) cresce exatamente como g(n), a menos de constantes.

f(n) é θ(g(n)) se existem c₁, c₂, m > 0 tais que c₁·g(n) ≤ f(n) ≤ c₂·g(n) para todo n ≥ m.
ω
Pequeno-ômega

Como Ω, mas mais restritiva: f(n) cresce estritamente mais rápido do que g(n), para qualquer constante c.

f(n) é ω(g(n)) se, para toda constante c > 0, existe m > 0 tal que f(n) > c·g(n) para todo n ≥ m.
ο
Pequeno-o

Como O, mas mais restritiva: f(n) cresce estritamente mais devagar do que g(n), para qualquer constante c.

f(n) é ο(g(n)) se, para toda constante c > 0, existe m > 0 tal que f(n) < c·g(n) para todo n ≥ m.
Σ
Regra da soma

Ao encadear dois algoritmos, o custo total é dado pelo maior deles.

O(f(n)) + O(g(n)) = O(max(f(n), g(n)))
O(n) + O(n²) = O(n²)
Se dois algoritmos em sequência custam O(n) e O(n²), o custo total do par é O(n²) — o menor termo se torna irrelevante. Da mesma forma, O(n) + O(n log n) = O(n log n).
07 Hierarquia de crescimento

As classes de complexidade mais comuns

Da mais rápida para a mais lenta — a mesma ordem que você viu no gráfico acima.

O(1)Constante — número fixo de instruções, independente do tamanho da entrada.
O(log n)Logarítmica — típica de algoritmos que reduzem o problema pela metade a cada passo.
O(n)Linear — uma quantidade fixa de operações por elemento de entrada.
O(n log n)Log-linear — algoritmos que particionam os dados, resolvem cada parte e depois combinam.
O(n²)Quadrática — comum quando dados são processados aos pares, com dois laços aninhados.
O(n³)Cúbica — três estruturas de repetição aninhadas.
O(2ⁿ)Exponencial — comum em soluções de força bruta; pouco prática para entradas grandes.
O(n!)Fatorial — força bruta no limite; cresce mais rápido que qualquer classe anterior.

O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(n³) < O(2ⁿ) < O(n!)
